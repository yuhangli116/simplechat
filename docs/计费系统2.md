## 一、现有系统完整计费逻辑

### 1.1 整体架构

系统采用 **钻石虚拟货币** 模型，用户通过购买会员或加油包获取钻石，使用AI模型时按Token消耗扣减钻石。

```
用户充值 → 获得钻石 → 调用AI模型 → 按倍率扣减钻石
```

技术栈：
- 前端：React + TypeScript + Zustand 状态管理
- 后端：Supabase PostgreSQL RPC 函数（SECURITY DEFINER）
- AI代理：Node.js Express 服务（server/aiProxy.js）

### 1.2 钻石定价体系

| 项目 | 数值 |
|------|------|
| 基准汇率 | 1 元 = 250,000 钻石 |
| 基准模型 | DeepSeek-V3 输入Token |
| 目标毛利率 | 50% |

### 1.3 双余额系统

用户钻石分为两类独立管理：

| 类型 | 来源 | 有效期 | 扣减优先级 |
|------|------|--------|-----------|
| 会员钻石 (member_diamonds) | 购买会员套餐 | 随会员到期作废 | 优先扣减 |
| 永久钻石 (permanent_diamonds) | 加油包/注册赠送/福利 | 永久有效 | 其次扣减 |

### 1.4 模型倍率配置

当前系统支持10个模型，倍率存储在数据库 `model_pricing` 表和前端 `MODEL_PRICING` 常量中：

| 模型 | 输入倍率 | 输出倍率 | 思考倍率 | 缓存倍率 |
|------|---------|---------|---------|---------|
| DeepSeek-V3 | 1x | 4x | - | 0.4x |
| DeepSeek-V3.2 | 1x | 1.5x | - | 0.1x |
| DeepSeek-R1 | 2x | 8x | 8x | 0.8x |
| Claude Haiku | 3.5x | 17.5x | - | 0.35x |
| Claude Sonnet | 10.5x | 52.5x | - | 1.05x |
| Claude Opus | 17.5x | 87.5x | - | 1.75x |
| GPT-4 Turbo | 7x | 28x | - | - |
| GPT-4o | 8.75x | 35x | - | - |
| Gemini 2.5 Pro | 4.375x | 35x | - | - |
| Gemini 3.1 Pro | 7x | 42x | - | 0.7x |

### 1.5 钻石消耗计算

```
消耗钻石 = CEIL(输入Token × 输入倍率 + 输出Token × 输出倍率 + 思考Token × 思考倍率 + 缓存Token × 缓存倍率)
```

### 1.8 福利系统

**新用户注册**：赠送 50万钻石（永久）

**新手签到**（注册后7天内）：
- 每天签到奖励 10,000 钻石
- 第7天奖励 20,000 钻石
- 7天累计：80,000 钻石

**任务奖励**：
| 任务 | 奖励 | 限制 |
|------|------|------|

| 首次创建模板 | 5,000 钻石 | 一次性 |
| 观看广告 | 50,000 钻石 | 每日一次 |

### 1.9 核心扣费流程 (deduct_diamonds_v4)

```
1. 验证用户身份 (auth.uid())
2. 从 model_pricing 表查询模型倍率
3. 获取用户余额（行锁 FOR UPDATE）
4. 检查会员是否过期 → 过期则清零会员钻石
5. 计算所需钻石 = CEIL(各Token × 对应倍率)
6. 检查总余额是否充足
7. 优先扣会员钻石，不足部分扣永久钻石
8. 更新 profiles 表余额
9. 写入 usage_logs 消费记录
10. 清理过期日志
11. 返回消费明细
```

### 1.10 充值流程

```
1. 前端调用 create_recharge_order RPC → 创建 pending 订单
2. 用户完成支付（当前为模拟支付）
3. 调用 process_membership_purchase 或 process_fuel_pack_purchase RPC
4. RPC 幂等处理：检查订单状态，防止重复处理
5. 更新用户余额和会员状态
```

### 1.11 安全机制

- 所有余额修改通过 `SECURITY DEFINER` RPC 函数执行
- 行级锁 (`FOR UPDATE`) 防止并发扣减竞态
- 订单幂等性保证（检查 status = 'pending'）
- 已移除用户直接修改 profiles 的 RLS 策略
- 前端无法绕过服务端扣费逻辑

### 1.12 日志管理

- `usage_logs`：消费记录，7天TTL自动清理
- `recharge_logs`：充值记录，100天TTL自动清理
- 清理通过 `cleanup_expired_diamond_logs()` 函数执行

### 1.13 游客模式

- 未登录用户使用 localStorage 存储余额（默认 9,999 钻石）
- 仅供体验，不与服务端同步

## 二、计费系统评估

### 2.1 优点

#### 架构设计

1. **双余额分离管理**：会员钻石（有期限）和永久钻石（无期限）分开存储，消费优先级清晰，既保护了平台利益（会员到期作废），又保障了用户权益（加油包永不过期）。

2. **原子性扣减**：使用 PostgreSQL 行锁 + 单事务完成余额检查和扣减，杜绝了超卖和并发竞态问题。

3. **幂等性设计**：充值回调通过订单状态检查实现幂等，即使重复调用也不会重复发放钻石。

4. **安全隔离**：所有余额操作通过 SECURITY DEFINER 函数执行，前端无法直接修改余额。

#### 商业模型

5. **定价锚定清晰**：以 DeepSeek-V3 输入Token为基准（1x），其他模型按成本比例设置倍率，逻辑透明。

6. **毛利率可控**：50%目标毛利率，通过倍率 = 官方成本 × 2 实现，简单可验证。

7. **产品分层合理**：会员（高频用户）+ 加油包（按需用户）覆盖不同消费习惯。

8. **新用户引导**：50万注册赠送 + 签到 + 任务，形成完整的新手引导漏斗。

#### 技术实现

9. **前后端一致**：前端 `MODEL_PRICING` 用于预估展示，后端 `model_pricing` 表用于实际扣费，保证了用户预期与实际消费一致。

10. **日志TTL机制**：自动清理过期日志，避免数据库无限膨胀。

### 2.2 存在的问题与改进建议

#### 问题1：前后端定价数据双重维护

**现状**：模型倍率同时硬编码在前端 `src/services/billing.ts` 和数据库 `model_pricing` 表中。

**风险**：修改定价时需要同步更新两处，容易遗漏导致前端显示与实际扣费不一致。

**建议**：前端启动时从数据库拉取定价配置并缓存，移除前端硬编码。或者至少增加版本号校验机制。

---

#### 问题2：会员过期处理时机不当

**现状**：会员过期检查仅在 `deduct_diamonds_v4` 扣费时触发。如果用户会员过期后未使用AI，其 `member_diamonds` 不会被清零，前端仍显示有余额。

**风险**：用户看到有余额但实际使用时才发现被清零，体验差。

**建议**：
- `getUserBalance` 查询时也检查过期状态
- 或增加定时任务批量处理过期会员
- 前端根据 `membership_expires_at` 主动标记"即将过期"

---

#### 问题3：计费发生在客户端而非服务端

**现状**：`src/services/ai.ts` 在前端调用AI后，由前端发起扣费RPC。

**风险**：
- 用户可以拦截网络请求，使用AI后不调用扣费接口
- 网络中断时AI已响应但扣费失败，造成损失
- Token计数依赖API返回值，部分情况下使用估算（`text.length / 1.5`）

**建议**：将计费逻辑移至服务端（aiProxy.js），AI响应返回前先完成扣费，或采用"预扣-结算"模式：
1. 请求前预扣估算金额
2. AI响应后按实际Token结算差额

---

#### 问题4：游客模式安全隐患

**现状**：游客使用 localStorage 存储余额（9,999钻石），清除浏览器数据即可无限重置。

**风险**：被滥用白嫖API调用，产生实际成本。

**建议**：
- 游客模式增加IP/设备指纹限制
- 或取消游客免费额度，改为注册后才能使用
- 至少在服务端记录游客调用量

---

#### 问题5：缺少预扣费/余额预检

**现状**：用户发起AI请求时不检查余额，等AI响应完成后才扣费。

**风险**：余额不足的用户仍能发起请求，消耗API成本后才发现无法扣费。

**建议**：在AI请求发起前，根据模型和预估输入Token做余额预检。余额不足时直接拒绝请求。

---

#### 问题6：Token估算精度问题

**现状**：当API未返回token usage时，使用 `text.length / 1.5` 估算。

**风险**：中文场景下token/字符比例与英文不同，估算偏差可能较大，导致多扣或少扣。

**建议**：
- 使用 tiktoken 等库做更精确的本地估算
- 或强制要求API返回usage（大部分主流API都支持）
- 记录估算vs实际的偏差率，用于校准

---

#### 问题7：缺少费用封顶/异常检测

**现状**：单次调用无消费上限，无异常消费告警。

**风险**：
- 超长对话可能单次消耗大量钻石，用户无感知
- 恶意调用或bug可能快速耗尽用户余额

**建议**：
- 设置单次调用最大消耗上限（如100万钻石），超出需用户确认
- 增加异常消费检测（如1小时内消费超过日均3倍触发告警）
- 在对话界面实时显示本次对话累计消耗


---

#### 问题8：会员续费时钻石累加问题

**现状**：`process_membership_purchase` 中，续费时直接 `member_diamonds = member_diamonds + p_diamonds`，会员期限叠加。

**风险**：用户在会员快到期时还剩大量钻石，续费后新旧钻石混在一起，但过期时间统一延长。这对平台有利但逻辑不够精确——旧钻石本应按原到期时间作废。

**建议**：当前实现对用户友好（续费等于延期所有钻石），可以保留。但建议在文档中明确这一规则，避免后续产生争议。

---

### 2.3 总结评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构设计 | 8/10 | 双余额+原子扣减+幂等性，设计扎实 |
| 安全性 | 6/10 | 服务端RPC安全，但客户端计费是重大漏洞 |
| 商业模型 | 8/10 | 定价合理，分层清晰，毛利可控 |
| 用户体验 | 7/10 | 福利系统完善，但缺少消费预警和实时反馈 |
| 可维护性 | 6/10 | 前后端双重维护定价，迁移文件较多 |
| 合规性 | 5/10 | 日志保留期过短，缺少退款机制 |

**综合评价**：计费系统核心逻辑设计合理，数据库层面的安全保障到位。最大的改进优先级是：**将计费从客户端移至服务端**，其次是**增加预扣费机制**和**延长日志保留期**。商业模型本身定价合理，产品分层清晰，具备上线基础。

#### Q1：`cache_hit_tokens` 解析逻辑存在语义错误

**文件**：`server/aiProxy.js` 第 145-152 行

**现状**：
```js
cache_hit_tokens:
  usage?.prompt_tokens_details?.cached_tokens ??
  usage?.input_tokens_details?.cached_tokens ??
  usage?.cached_tokens ??
  usage?.cached_context_tokens ??
  usage?.cache_creation_input_tokens ??   // ← 问题在此
  usage?.cache_read_input_tokens ??
  0,
```

**问题**：
1. `cache_creation_input_tokens` 表示"写入缓存的 token"（缓存未命中，首次创建缓存），NOT 缓存命中。将其作为 `cache_hit_tokens` 的 fallback 语义上是错误的。
2. `??` 运算符只在左侧为 `null/undefined` 时才继续。如果 DeepSeek 返回 `cache_creation_input_tokens: 0`（数字 0 不是 nullish），链条会停在此处，永远不会读到下面的 `cache_read_input_tokens`。

**影响**：
- 场景 A（首次请求，创建缓存）：`cache_creation_input_tokens = 500`，会被当作"缓存命中"计入，按极低的 0.01x 计费 → **平台少收钱**
- 场景 B（后续请求，缓存命中）：如果同时返回 `cache_creation_input_tokens: 0` 和 `cache_read_input_tokens: 1000`，链条停在 0 → 缓存命中 token 被忽略，全部按正常输入 0.5x 计费 → **用户多花钱**

**修复建议**：
```js
cache_hit_tokens:
  usage?.prompt_tokens_details?.cached_tokens ??
  usage?.input_tokens_details?.cached_tokens ??
  usage?.cached_tokens ??
  usage?.cached_context_tokens ??
  usage?.cache_read_input_tokens ??    // 只保留 read，移除 creation
  0,
```

#### Q2：计费公式可能存在缓存 token 双重计费

**文件**：`server/aiProxy.js` 第 269-275 行

**现状**：
```js
const calculateDiamondCost = (pricing, usage) =>
  Math.ceil(
    (usage?.input_tokens ?? 0) * pricing.input_multiplier +
    (usage?.output_tokens ?? 0) * pricing.output_multiplier +
    (usage?.reasoning_tokens ?? 0) * pricing.reasoning_multiplier +
    (usage?.cache_hit_tokens ?? 0) * pricing.cache_multiplier
  );
```

**问题**：DeepSeek API（遵循 OpenAI 格式）中，`prompt_tokens` 是输入的**总量**（包含缓存命中部分）。`prompt_tokens_details.cached_tokens` 是其中命中缓存的子集。

如果 `input_tokens = 1500`（含 1200 缓存命中），正确的计费应为：
```
(1500 - 1200) × 0.5 + 1200 × 0.01 = 150 + 12 = 162 钻石
```

但当前公式计算为：
```
1500 × 0.5 + 1200 × 0.01 = 750 + 12 = 762 钻石（多收 4.7 倍！）
```

**影响**：如果 DeepSeek 的 `prompt_tokens` 包含缓存 token（很可能如此），用户会被严重多扣钻石。

**修复建议**：
```js
const calculateDiamondCost = (pricing, usage) => {
  const inputTokens = usage?.input_tokens ?? 0;
  const cacheHitTokens = usage?.cache_hit_tokens ?? 0;
  const nonCachedInput = Math.max(0, inputTokens - cacheHitTokens);
  
  return Math.ceil(
    nonCachedInput * pricing.input_multiplier +
    cacheHitTokens * pricing.cache_multiplier +
    (usage?.output_tokens ?? 0) * pricing.output_multiplier +
    (usage?.reasoning_tokens ?? 0) * pricing.reasoning_multiplier
  );
};
```

**注意**：Supabase RPC `deduct_diamonds_v4` 中的计算逻辑也需要同步修改（如果 RPC 内部也是直接 `p_input_tokens * input_mult + p_cache_tokens * cache_mult` 的话）。

### 6.5 本地体验性能优化建议（2026-05-31）

当你在本地预览环境进行正文续写时，如果出现“单次生成需要 30–40 秒”的体验，通常是多段链路叠加造成（总结一次 + 续写一次 + 多次 DB 往返 + 跨境网络）。以下是三项对体验提升最明显、且与计费闭环兼容的优化建议：

#### O1：流式输出（streaming）

**目标**：让正文边生成边展示，用户体感从“等待 30–40 秒”变成“1–3 秒开始出字”。  
**说明**：总耗时可能接近，但体验提升最大；同时也能减少用户误以为“卡死/没响应”的概率。

**实现方向（摘要）**：
- 后端：`/api/ai/generate` 支持 `stream: true`，通过 SSE/ReadableStream 将增量 token 片段推送给前端
- 前端：编辑器逐段接收并插入内容，同时在提示词对话框内显示“生成中”状态

#### O2：缓存总结结果（按 updated_at 失效）

**目标**：对同一份“参考大纲/设定”在短时间内重复使用时，不再每次都 summarize。  
**失效条件**：当引用的思维导图节点发生变更（例如 `mind_maps.updated_at` 变化）才重新总结。

**实现方向（摘要）**：
- 以 `(workId, nodeId, nodeUpdatedAt, model)` 作为缓存键（或 hash）
- 缓存位置：服务端内存缓存（TTL）或 Supabase 表（持久化缓存）
- 命中缓存时：跳过 `/api/ai/summarize`，直接进入 `/api/ai/generate`

#### O3：服务端缓存 model_pricing（TTL）

**目标**：减少每次 AI 调用前预算预检时对 `model_pricing` 的一次 DB 往返，从而降低延迟波动。  
**说明**：对总耗时提升不如 streaming，但属于“稳定收益”，且实现成本低。

**实现方向（摘要）**：
- 服务端对 `getModelPricingFromDb(modelKey)` 做内存 TTL 缓存（例如 60–300 秒）
- 缓存失效后再拉取最新定价；或在 `system_config.pricing_version` 变化时主动清缓存
